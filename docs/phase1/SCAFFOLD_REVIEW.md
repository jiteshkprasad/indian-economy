# Phase 1 pipeline framework: review log

An independent reviewer checked the framework (reproducibility, schema contract, fetch policy, template unit values) on 2026-09-29. They found no blocker, 8 major and 8 minor issues. The framework author re-checked each issue, fixed it or rejected it, and recorded the outcome here. The areas the reviewer found sound (byte-identical rebuilds, contract rejections, challenge detection with status 200, the template's 14 checked values) were not changed, apart from the template's raw-file paths (R8).

Every issue was reproduced before it was fixed, either with the reviewer's own probes (`probe_contract.py`, `probe_fetch.py` with `server.py`) or with the scenario described in the evidence. Each fix has a regression test.

## Issues and dispositions

| # | Severity | Issue (short) | Disposition | What was done / reason | Test |
|---|---|---|---|---|---|
| R1 | major | Swapping in a unit's output is not atomic on Windows; `rmtree` half-deletes the folder, and the manifest then describes the broken state. | FIXED | Confirmed: `rmtree` on a folder holding an open file deletes some files, then raises. The swap is now renames only: rename the old folder aside, then rename the temp folder in, then delete the old one (best effort). If the first rename fails (WinError 5 with a file open), nothing changes, the temp folder is removed and the build fails with "previous output is unchanged". Leftover `.<unit>.tmp-*` and `.<unit>.old-*` folders are swept at the start of every build, under the repo lock. The disk is therefore always a complete old or new state, so regenerating the manifest afterwards is correct. Re-ran the reviewer's scenario (a background `open()` handle during `build`): build failed cleanly, all 4 files and `data/manifest.json` kept their sha256, and no temp folder was left. | `test_swap_failure_keeps_previous_output_and_leaves_no_debris`, `test_open_file_in_output_on_windows` |
| R2 | major | A bot challenge served with HTTP 5xx is retried 4 times and reported as a generic `FetchError`. | FIXED | Every 429/5xx body is scanned for challenge markers before a retry; a match raises `AccessBlocked` at once. `detect_block` also flags markers on any status >= 400. Re-ran the reviewer's server: `/cf503` was requested once (was 4 times), and the result is `AccessBlocked (Cloudflare challenge)`. | `test_challenge_served_with_5xx_is_blocked_without_retry`, `test_detect_block[...503...]` |
| R3 | major | D1-1c (no GSTN/CBDT) and D1-2 (no microdata) exist only in the docs; `gstn_gst_statistics` (`requires: none`) could be fetched. | FIXED (with a documented exception list) | New `pipeline/core/policy.py`. It refuses source ids `gstn_*`, `cbdt_*`, `*_unit_data` and `*microdata*`; sources whose landing page is on a denied host; and any source whose registry `access.requires` is not `none`. Denied hosts, and their subdomains, are never contacted, including on redirects: gst.gov.in, incometax.gov.in, incometaxindia.gov.in and microdata.gov.in. It is checked in `check_contract`, which covers SOURCES for both fetch and build, in `fetch_file`, and at every redirect hop. **Partial deviation from the suggested fix:** refusing every `requires != none` source outright would also block public parts that the registry itself documents. Three sources get URL-prefix exceptions (`PUBLIC_PARTS`): `mospi_asi` (keyless ASI API and PDFs), `cag_state_finance_accounts` (public PDFs), and `un_comtrade` (keyless preview). This is logged as fw-15 for the orchestrator to confirm. `gst_monthly_state_revenue`, a GSTN PDF with `requires: none`, is caught by the denied-host rule. | `test_access_policy_refuses_sources` (7 sources), `test_access_policy_public_parts_and_hosts`, `test_policy_guards` |
| R4 | major | The per-host 2 s limit is shared only within one raw folder; scratch layouts and live tests bypass it; redirect hops are not rate-limited or checked. | FIXED | Host locks and last-request stamps moved to one machine-wide, per-user folder that does not depend on the layout or checkout (`paths.host_lock_dir()`: `%LOCALAPPDATA%\india-sam\host-locks`, `~/.cache/...` on POSIX, overridable with `INDIA_SAM_HOST_LOCK_DIR`). The lock key is the host, plus the port when one is given. httpx now runs with `follow_redirects=False`. Redirects are followed by hand, at most 5 hops. Each hop goes through the policy checks (denied host, login page, http(s) only) before it is requested, then through the same host lock and 2 s wait. The chain is recorded in `.meta.json` (`redirects`). | `test_host_lock_is_shared_across_layouts`, `test_redirects_are_followed_by_hand_with_rate_limit_and_policy` |
| R5 | major | A killed process leaves a stale lock (repo lock and host locks) that blocks everyone for about 30 min. | FIXED (different mechanism) | Instead of checking whether the pid is alive, both locks are now OS locks: `msvcrt.locking` on Windows, `flock` on POSIX (new `pipeline/core/locks.py`). The OS releases them when the holder dies, however it dies, so no lock can go stale and none is ever "broken". That avoids the race where two waiters both break a dead lock and one deletes the other's new lock. The lock file is never deleted. The holder's pid, host and start time go to `<lock>.holder`, used only for messages. Also note that `os.kill(pid, 0)`, as suggested, would terminate the process on Windows. Re-ran the reviewer's `echo 99999 > data/.pipeline.lock; build`: the build finished in 1.3 s (it previously blocked for more than 25 s). | `test_live_holder_blocks_and_killed_holder_releases` (holder killed with TerminateProcess; the lock is free in under 5 s), `test_leftover_lock_file_from_old_code_does_not_block`, `test_lock_is_exclusive_within_one_process` |
| R6 | major | One malformed `registry_additions/<unit>.yaml`, or two files adding the same id, breaks every unit. | FIXED | Each addition file is validated on its own. A file that is not valid YAML, has the wrong `unit`, or is named after a unit that does not exist is ignored, and its problems are attributed to that unit only. An invalid entry, or an id added by two files, is marked unusable: only the owning units, and any unit that lists that id, fail (`RegistryError`). `registry.yaml` itself (orchestrator-owned) still fails hard. `check_contract` fails a unit whose own addition file has problems. New generic test `test_registry_additions_valid[<unit>]`. Re-ran the reviewer's probe (`zz_probe.yaml` with a duplicate `rbi_hbs` entry that lacks fields): `build mospi_nas_2026` passed, and `test` gave 1 failure (`test_registry_additions_valid[zz_probe]`) instead of 28. | `test_registry_addition_rules`, `test_broken_addition_file_affects_only_its_unit`, `test_same_id_added_by_two_units_breaks_both_owners_only` |
| R7 | major | Provenance can be empty for derived/estimated rows, and wrong for unit conversions (Rs lakh with conversion none; US$ on INR rows). | FIXED | (a) A `derived` record needs `inputs` or `raw`. An `estimated` record needs `inputs`, `raw`, or `notes` citing its basis. This is enforced in `ctx.prov()` (early) and in `validate_provenance`, which also covers data on disk. (b) New `runner.check_units_against_provenance`, applied to every (prov_id, row unit) pair. Official `INR_crore` rows need a rupee caption. Whenever the caption is a rupee unit, `conversion` must start with `units.conversion_note(key)`. INR rows whose caption says US$ must be `derived`, with an input whose rows have unit `INR_per_USD` (the unit's own rows or a DEPENDS unit's clean files). Dollar rows may not carry a rupee caption. The template passes unchanged. All 4 of the reviewer's probe cases are now rejected. | `test_row_units_must_agree_with_provenance` (5 cases), `test_consistent_units_pass`, `test_dollar_rows_in_rupees_need_a_rate_series`, `test_derived_and_estimated_records_must_be_traceable`, `test_provenance_rules` |
| R8 | major | Two units can collide on raw file names (same source, same name, same day), with a misleading error. | FIXED | The raw path now includes the unit: `data/raw/<source_id>/<date>/<unit>/<name>`. Separately, a path that already holds other bytes, or that any current or superseded pin uses for other bytes, is never reused: a second version on the same day goes to `<date>-r2/`. The old "fetched twice today" error is gone. The guide now asks for names built from the publisher's table id. The template's 3 pinned files were moved into the new layout with bytes unchanged (sha256 re-verified); its pins were updated and it was rebuilt, so its prov_ids and clean-file hashes changed once (fw-16). `test_pinned_raw_file` now asserts the layout. | `test_upstream_change_creates_new_pin_and_never_overwrites`, `test_pinned_raw_file[...]` |
| R9 | minor | A plain `fetch` whose pinned file is missing silently re-pins if upstream bytes changed, and reuses the old pin's path. | FIXED | This case now fails with "cannot be restored ... run `fetch <unit> --refresh`" and saves nothing. With `--refresh` the new bytes go to a path that no pin has used for other bytes. `REVISION` messages now go through `ctx.warn`, so they appear in the run summary. | `test_restoring_a_missing_pinned_file_never_silently_repins` |
| R10 | minor | `build <unit>` also rebuilds, and rewrites, every unit in DEPENDS. | FIXED | `build <unit>` reads dependencies as already built. If one has no clean output it fails with a clear message, and it never writes another unit's folder. `--with-deps` rebuilds them. `build` with no units, and `repro` (which builds into scratch folders), still build the full chain. Documented in guide §3. | `test_build_does_not_rebuild_dependencies_unless_asked` |

| R12 | minor | Format checks accept impossible values: date 2024-02-31, vintages 2026-13-45 / 0000-00-00 / future, unsorted `dim_other`, geography 'India', a period after its vintage. | FIXED | `date` periods must be real calendar dates. Other stage-to-period rules are unit-specific and stay in unit tests. | `test_format_checks` (9 cases), `test_format_checks_accept_valid_values` |
| R13 | minor | A long Retry-After is capped and retried early; HTTP-date Retry-After is ignored; the header denylist is short; local protocol errors are retried. | FIXED | A Retry-After above 120 s now stops with `AccessBlocked` instead of retrying early, and the HTTP-date form is parsed.
